# Calendriers publiés par les plugins

`PublishedCalendarMixin` permet à un plugin actif de publier ses propres calendriers sans exposer ses modèles. Le registre existant découvre les fournisseurs par le mixin `publishedcalendar`. Le slug du plugin et l'identifiant local immuable du calendrier forment l'identité globale. Deux fournisseurs peuvent employer le même identifiant local.

Un fournisseur implémente `list_published_calendars(user)` pour les métadonnées visibles, `get_published_calendar(user, calendar_id)` pour vérifier un calendrier précis, puis `get_published_events(user, calendar_id, start, end)` pour les événements. Il retourne `PublishedCalendar` et `LabsManagerCalendarEvent` du cœur. Les identifiants locaux sont des chaînes alphanumériques avec `_` ou `-`. Si le stockage peut réutiliser un identifiant local après suppression, `PublishedCalendar.incarnation` contient une valeur immuable propre à l'instance créée ; ICalExport la lie à la signature de l'abonnement. Calendars utilise `created_at`. Les bornes `start` et `end` sont des datetimes Django ; l'intervalle est `[start, end)` et les événements qui le chevauchent doivent être retournés. Le fournisseur conserve entièrement ses règles de visibilité. Le consommateur appelle de nouveau `get_published_calendar` à chaque lecture, car les droits peuvent changer après la création d'un abonnement.

Les événements du DTO existant portent titre, description, dates, journée entière et métadonnées facultatives. `metadata["last_modified"]` peut porter un datetime ; `metadata["assignees"]` peut porter une liste de `{name, email?}` déjà filtrée selon les droits du lecteur. Aucune adresse d'employé n'est requise. La liste des calendriers ne lit pas leurs événements. Une déclaration invalide ou une erreur de liste d'un fournisseur est isolée des autres fournisseurs.

`CalendarSubscriptionMixin` déclare un consommateur actif pour un format (`subscription_format = "ics"`). L'API générique `GET /api/v1/published-calendars/subscriptions/` annonce les formats disponibles. `POST /api/v1/published-calendars/<plugin_slug>/<calendar_id>/subscriptions/` vérifie le droit de lecture avant d'appeler le consommateur ; la réponse contenant l'URL personnelle n'est pas mise en cache. Le frontend d'un fournisseur n'a donc aucun chemin ou import propre au consommateur. Si celui-ci est désactivé ou si ses URLs sont indisponibles, aucun format n'est annoncé.

ICalExport consomme ce contrat pour les abonnements ICS individuels. Il signe ensemble l'identifiant public du token, le slug et l'identifiant du calendrier. À chaque téléchargement, il valide le token personnel, le plugin actif, le calendrier encore disponible et les droits du titulaire, puis charge uniquement les événements du calendrier demandé. Son URL native et ses abonnements existants restent inchangés. Les nouveaux flux utilisent l'URL `ics/external/<plugin_slug>/<calendar_id>/` et la même période bornée que les flux natifs. Les UID des événements incluent l'identité du fournisseur et du calendrier ; renommer un calendrier ou un événement ne les change pas. La révocation utilise la gestion existante des tokens.

Calendars est un exemple de fournisseur. Il publie les calendriers visibles selon ses droits `view` et sélectionne les événements qui chevauchent la période demandée. Les noms des employés affectés sont limités aux fiches visibles par le titulaire du flux. Il continue de fonctionner sans ICalExport.

`PublishedCalendar.options` annonce les options facultatives du calendrier. Calendars déclare `("assigned_to_me",)` uniquement pour le type `assignments`. Le consommateur transmet cette option à `get_published_events(..., options={"assigned_to_me": True})` après validation ; les fournisseurs sans option conservent l'ancienne signature à quatre arguments. Le fournisseur applique le filtre dans sa requête métier. Dans un abonnement ICS, l'identité de référence est celle du propriétaire du token, jamais celle de la requête anonyme. `assigned_to_me=1` ne fait que restreindre le flux déjà autorisé : les tokens et scopes signés ne changent pas. Une option non annoncée ou une valeur autre que `0` ou `1` est refusée.

Les métadonnées facultatives `metadata["links"]` contiennent des chemins React relatifs à la base publique `/app/`, déjà filtrés selon les droits du propriétaire. ICalExport les transforme avec le helper React existant et les ajoute à `DESCRIPTION` avec le formatage des liens natifs ; les descriptions métier et les UID sont conservés. Plusieurs destinations peuvent être fournies sans dupliquer les liens.

Aucune nouvelle table ni migration n'est requise pour ce contrat. La migration `0003` de Calendars appartient à sa version précédente ; vérifier son état avant les tests d'intégration ou un déploiement.
