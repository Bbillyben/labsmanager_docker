# Registres et contrats d’extension de LabsManager

Ce document décrit le **code courant**. « Extension » signifie ici un point d’ajout explicite ou une table de définitions maintenue dans le dépôt ; cela ne signifie pas chargement dynamique de JavaScript. Les chemins sont relatifs à la racine du dépôt. Les exemples sont indicatifs et doivent conserver les contrôles de visibilité de leur domaine.

## Plugins et mixins

### Purpose et location

Le registre principal charge les plugins, suit leur état actif/inactif et expose les mixins aux sous-systèmes. Lire [registry.py](../../backend/plugin/registry.py), [plugin.py](../../backend/plugin/plugin.py), les classes de [base](../../backend/plugin/base/) et les [tests plugin](../../backend/plugin/tests.py). Ce registre n’autorise pas à contourner les permissions des données retournées par un plugin.

### Registration / discovery et lifecycle

Le loader découvre les modules plugin internes/externes, instancie leurs classes et enregistre les mixins déclarés par `add_mixin(key, fnc_enabled=True, cls=None)`. `MixinMeta.MIXIN_NAME` nomme le mixin ; la clé technique est celle de `add_mixin`, par exemple `dashboard`, `search` ou `calendarevent`. `mixin_enabled(key)` tient compte du booléen ou callable enregistré. `registry.with_mixin(mixin: str, active=True, builtin=None)` déclenche le rechargement nécessaire et ne renvoie que les plugins portant le mixin et, par défaut, actifs. Les familles `schedule`, `calendarevent`, `mailsubscription` sont aussi pilotées par leurs réglages `ENABLE_PLUGINS_*`. Dashboard et Search ne disposent pas d’un interrupteur de famille analogue dans ce filtre. La disponibilité dépend donc de l’état réel du plugin et du mixin.

Découverte → chargement du plugin → enregistrement de mixins → filtrage actif/configuration → appel par le registre métier → API. Une erreur de chargement figure dans les erreurs du registre ; une erreur d’une contribution Dashboard/Search/Calendar est isolée par ces services (voir ci-dessous), sans rendre automatiquement les autres contributions invalides.

### Contract objects et callbacks

`LabManagerPlugin` combine `VersionMixin`, `MixinBase` et `MetaBase`. `MixinBase.add_mixin` enregistre une capacité ; `mixin_enabled` est le test opérationnel ; `get_registered_mixins` expose ses classes de mixin. Les mixins métiers donnent leurs callbacks propres : `DashboardPluginMixin.get_dashboard_sources(context)` / `get_dashboard_widgets(context)` ; `SearchPluginMixin.get_search_providers(user)` ; `CalendarEventMixin.get_calendar_events(context)`, `get_calendar_filters(context)` et `filter_calendar_queryset(queryset, context)`. Leur valeur par défaut est vide ou le queryset inchangé. Les callbacks doivent conserver la visibilité de l’utilisateur, renvoyer les types attendus et éviter les traitements coûteux non bornés. Les détails des objets retournés sont dans les sections métier.

Les autres contrats historiques sont distincts : `SettingsMixin` enregistre `settings` si `has_settings()` et expose `get_setting(key,cache=False,backup_value=None)` / `set_setting(key,value,user=None)` ; `ScheduleMixin` enregistre `schedule` si `has_scheduled_tasks()` et gère `get_scheduled_tasks()` / `register_tasks()` ; `MailSubscriptionMixin` enregistre `mailsubscription` et expose `add_context(user,current_context)` / `get_template()` ; `ReportMixin` enregistre `report` et expose `add_report_data(current_report,request,context)` ; `UrlsMixin` enregistre `urls` si `has_urls()` et expose `urlpatterns()`, `setup_urls()` et `setup_api_urls()`. Voir leurs fichiers dans [base](../../backend/plugin/base/) avant de contribuer : leurs contrats et hooks d’activation sont historiques, et aucun n’implique automatiquement une UI React.

### Validation, frontend bridge, failure, stability

Le registre plugin est une infrastructure historique ; ses clés de mixin sont un contrat utilisé par les sous-systèmes, mais la structure interne de discovery/reload n’est pas une API à recopier. Les clés du plugin, son état et ses mixins sont visibles via les API d’administration plugin, pas via un chargeur React générique. Un plugin désactivé disparaît des consultations `active=True`. Exemple réel : [FrenchHollidayPlugin](../../backend/plugin/samples/FrenchHollidayPlugin/FrenchHollidayPlugin.py) combine Calendar, Settings, Schedule et Dashboard. Les tests métier de chaque consommateur complètent les tests plugin.

## Dashboard backend : sources, widgets et templates

### Purpose et location

Le registre agrège sources core et contributions plugin sans stocker leurs définitions en base ; seules les **instances** Dashboard le sont. Sources : [registry.py](../../backend/dashboard/registry.py), [api_v1.py](../../backend/dashboard/api_v1.py), [tests Dashboard](../../backend/dashboard/tests.py) et [exemple plugin](DASHBOARD_PLUGIN_EXAMPLE.md). Le catalogue pilote l’éditeur et le rendu des instances.

### Registration / discovery et contract objects

`CORE_SOURCES`, `CORE_WIDGETS`, `CORE_RENDERERS` et `TEMPLATES` sont statiques. `dashboard_registry(context)` y ajoute les résultats des plugins actifs `with_mixin("dashboard", active=True)`. Un plugin doit hériter de `DashboardPluginMixin` et retourner des séquences de `DataSource` / `WidgetDefinition`. La méthode synthétise une `WidgetDefinition` si une source sans widget explicite choisit un renderer **core** compatible. `available_definitions(context)` filtre les deux scopes, les deux callbacks `available` et la compatibilité source/renderer. `definition_for_template` retrouve un widget par source et renderer, avec fallback sur la première définition de la source.

`DashboardContext` est une dataclass figée : `context_type: str` (actuellement `user` ou `project` dans les catalogues actifs), `user: object` (utilisateur courant), `context_object: object = None` (racine métier). `personal(user)` et `for_object(user, object)` construisent ces contextes ; `for_project(user, project)` est un alias de compatibilité. Les propriétés `scope`, `object`, `object_id` et `project` conservent l’ancien contrat des providers. Une nouvelle source devrait utiliser `context_object`.

`DataSource` : `key: str` identifiant stable, `label: str`, `category: str`, `supported_scopes: tuple[str, ...]`, `compatible_renderers: tuple[str, ...]`, `provider: Callable` sont obligatoires. Facultatifs : `available(context)` (défaut vrai), `description=""`, `allow_multiple=False`, `default_renderer=""`, `config_fields={}`. La source possède la requête métier et la visibilité, non le composant React.

`WidgetDefinition` : obligatoires `key`, `title`, `category`, `renderer_key`, `source_key` (`str`). Défauts : `supported_scopes=("user",)`, `default_size=(4,3)`, `min_size=(2,2)`, `max_size=(12,8)`, `allow_multiple=False`, `printable=True`, `icon="LayoutDashboard"`, `config_fields={}`, `available(context)=True`. Elle lie une source à un renderer, aux tailles et au catalogue.

`TemplateWidget` : `source_key: str`, `renderer_key: str` obligatoires ; `config: dict={}`, `title: str=""`, `x/y/width/height: int | None = None` optionnels. Sans taille explicite, le service utilise `WidgetDefinition.default_size` ; toute taille demandée est bornée par `min_size`, `max_size` et, pour la largeur, les 12 colonnes desktop. Une position explicite n'est conservée que si x et y sont tous deux présents, dans la grille et sans collision ; sinon le service trouve la première position libre de gauche à droite puis de haut en bas. `logical_order` suit l'ordre de déclaration, pas la position graphique. `TEMPLATES` contient `employee`, `leader`, `lab-manager`, `blank`, `project` ; ces modèles créent des instances indépendantes et ne changent pas celles déjà créées. `CORE_RENDERERS` est un dictionnaire de métadonnées `{label, config_fields}` pour `kpi`, `compact-list`, `alert-list`, `progress-list`, `overview-list`, `deadline-list`, `contract-list`, `employee-movements`, `task-workload`, `empty`, `line-chart`, `data-consistency`. Ce n’est **pas** l’enregistrement des composants React.

Les nouveaux templates privilégient les renderers enrichis : Employee (charge personnelle, portefeuille Project, Tasks, Milestones, calendrier, Leaves), Leader (santé Project, charge des subordonnés, Tasks, Milestones, calendrier, Funds, Contracts, Leaves), Lab Manager (santé Project, Funds, Contracts, Milestones, calendrier, mouvements Employee et Data Consistency si autorisé), Project (santé du Project, calendrier, Tasks, Milestones, Funds, Contracts, évolution des dépenses). Le template Employee résout l'Employee lié au compte lors de la création et omet la charge personnelle si aucun Employee visible n'est lié. `core.employee-workload` ne possède pas de scope global : le template Lab Manager ne le force pas. La création API et la création contextuelle utilisent le même service de template et placent les widgets selon leur taille et position effectives sur une grille de 12 colonnes, sans modifier les instances existantes.

### Provider / payload / validation

Signature effective : `provider(context, config) -> dict` ; `config` est validée par l’API et la source doit appliquer les permissions métier et borner ses résultats. Payloads core connus : KPI `{value, label, context?, secondary?, tone?}` ; listes `{items: [{key, label, secondary?, date?, status?, href?, icon?, tone?, severity?, current?, total?, percent?}]}` ; texte `{message}` ; Data Consistency `{summary_url}` ; chart selon `financial_sources`. Une source multi-renderer peut retourner `{"__renderers__": {"kpi": {...}, "compact-list": {...}}}` : l’API extrait seulement la variante choisie. Les clés de payload restent le contrat du renderer concerné, non un schéma universel.

`core.funds` ajoute le renderer local `overview-list` sans retirer les autres ni les champs de configuration `project_scope`, `project_id`, `scope`, `active_only`, `ending_within_days`, `limit`. Sa définition explicite garde la clé persistée `core.funds` et donne une taille initiale `(6,5)` ; les instances antérieures restent valides. Son payload est `{summary:{amount:number,spent:number,percent:number|null,count:number,count_label:string,attention_count:number},items:[{key,label,secondary?,href?,date?,current,total,percent,remaining_days,status}]}`. `status` vaut `normal`, `ending_soon` ou `expired` ; `remaining_days` et `percent` peuvent être `null`. Les sommes et statuts viennent du backend, après visibilité et filtres ; `spent` utilise la valeur absolue de chaque dépense signée. Les noms restent métier, les libellés d’interface sont traduits en React. Le payload `progress-list` conserve ses anciens `items` et son rendu générique ; seules les instances `overview-list` utilisent la synthèse enrichie. Le renderer adapte seulement densité et formatage. Aucune devise n’est ajoutée au contrat, le modèle Fund n’en fournissant pas.

`core.milestones` ajoute `deadline-list` sans retirer `kpi`, `compact-list` ou `alert-list` ni ses champs `project_scope`, `project_id`, `scope`, `status`, `overdue_only`, `due_within_days`, `limit`. Sa définition garde la clé persistée `core.milestones`, avec taille initiale `(6,5)`. Payload : `{summary:{count:number,overdue_count:number,due_soon_count:number},items:[{key,label,project_name,date,href,days_until,state}]}`. `date` et `days_until` sont nullables ; `state` vaut `overdue`, `today`, `due_soon`, `upcoming`, `completed` ou `unscheduled`. Les compteurs portent sur le queryset visible **après** les filtres ; `due_soon_count` compte les jalons ouverts d’aujourd’hui à sept jours inclus. Le backend ordonne les jalons ouverts en retard, proches puis futurs avant les terminés et sans date. Les payloads `compact-list` et `alert-list` gardent leurs anciens `items` et leur rendu générique, y compris pour les instances persistées. Le renderer React se limite à la traduction, au formatage des dates et à la densité selon la taille.

`core.employees` ajoute `employee-movements` comme renderer par défaut tout en conservant les variantes `kpi`, `compact-list` et `alert-list`. Son payload dédié est `{summary:{count,arrivals_count,departures_count},items:[{key,name,href,role,team_name,team_href,state,date,days_until}]}`. Le queryset applique d’abord visibilité, scope Project/Employee, `active_only` et `movement` ; les compteurs de mouvements sont calculés ensuite dans la fenêtre `within_days`. Les lignes enrichies affichent en priorité les départs puis les arrivées, avec rôle et Team visibles ; les listes génériques restent inchangées.

`core.projects` propose `project-portfolio` comme renderer par défaut, sans migrer les instances existantes ni remplacer `kpi`, `compact-list` et `alert-list`. Payload dédié : `{summary:{count,active_count,ending_soon_count,attention_count},items:[{key,name,href,start_date,end_date,temporal_percent,temporal_state,financial,financial_delta,financial_state,next_milestone,overdue_task_count,overdue_milestone_count,attention_signals}]}`. `financial` est nullable ; `financial_delta = financial.percent - temporal_percent` est calculé seulement si les deux existent. Le backend classe l’écart à ±10 points inclus comme `on_track`, au-dessus comme `funding_ahead`, en dessous comme `funding_behind`. `attention_signals` contient les faits `overdue_tasks`, `overdue_milestones`, `project_ending_soon`, `project_ended`, `funding_ahead` et `funding_behind`, avec compte/écart et tonalité lorsque pertinents ; `on_track` reste dans `financial_state` et ne compte pas comme attention. `attention_count` compte chaque Project une seule fois. Les nombres en retard et la prochaine Milestone ouverte sont calculés côté backend ; le renderer varie uniquement la densité. La consommation réutilise `visible_funds` et `advancement_for_funds` sur les seuls Funds visibles. Aucun score de santé opaque n’est généré ; filtres et configuration restent ceux de `core.projects` dans la sidebar.

`core.projects` propose aussi `project-health-bars` comme renderer graphique facultatif, sans changer le défaut ni les instances. Son payload distinct utilise `__renderers__` : `{summary,items:[{key,name,href,milestones:{total,upcoming_count,imminent_count,overdue_count,unscheduled_count},tasks:{...},contracts:{total,active_count,ending_soon_count,expired_rh_active_count},funding:{amount,spent,percent,tone}|null,deadline:{percent,state,tone,relative},funding_pace:{applicable,ratio,state,tone}}]}`. Tasks/Milestones sont ouvertes (`status=false`) ; retard avant aujourd’hui, imminent d’aujourd’hui à `DASHBOARD_MILESTONES_STALE_TO_MONTH × 30` jours inclus, futur après, sans date séparément. Contracts : seul le suivi RH actif (`is_active=true`) et commencé entre dans la barre ; le rouge exige `end_date < today` et `is_active=true`, le bleu utilise `DASHBOARD_CONTRACT_STALE_TO_MONTH`, et les Contracts terminés avec suivi RH désactivé sont exclus. La visibilité utilise `visible_contracts`, `visible_funds` et les Projects du scope. `funding_pace = funding.percent / deadline.percent` n’est applicable que si la progression temporelle atteint 1 point ; l’axe cible 1,0, avec tonalité succès pour ±0,2, avertissement jusqu’à ±0,4, danger au-delà. Ce ratio descriptif n’est pas un score de santé.

`core.employee-workload` est une source/widget de Dashboard personnel avec renderer dédié `employee-workload`. Les scopes `single`, `team` et `subordinates` emploient les visibilités Employee, Team et Project existantes. Le payload `single` contient l’Employee et les quatre métriques `{key,value,unit,reference_value}` : allocation Project en pourcentage, Tasks ouvertes, Milestones ouverts et leur somme. Le payload `comparison` contient `{metric,unit,reference_value,items:[{employee_id,employee_name,value,href}]}` triés par valeur décroissante puis nom. L’allocation somme `Participant.quotity × 100` pour les Projects visibles, actifs et en cours aujourd’hui, sans plafond ; la quotité Contract n’intervient pas. La référence 100 % n’existe que pour l’allocation. Le choix d’Employee/Team et de métrique est validé côté API et reste dans la sidebar.

`core.tasks` ajoute `task-workload` comme renderer par défaut sans modifier `kpi`, `compact-list`, `alert-list` ni leurs instances persistées. Son payload dédié est `{summary:{count,overdue_count,due_soon_count},items:[{key,title,href,project_name,project_href,assignees,date,days_until,state}]}`. Les compteurs sont calculés après visibilité et tous les filtres ; `due_soon_count` utilise `due_within_days` lorsqu’il est défini, sinon le seuil utilisateur `DASHBOARD_MILESTONES_STALE_TO_MONTH` déjà employé par la source Planning. Les lignes priorisent les tâches ouvertes en retard, proches puis futures ; les liens vers les assignees ne sont fournis que pour les Employees visibles.

`core.timeline` est une source composite distincte de `core.tasks` et `core.milestones`, avec `timeline-calendar` comme renderer détaillé par défaut et `calendar-grid` comme variante compacte en grille hebdomadaire. Son registre de providers contient actuellement Tasks et Milestones. Il réutilise leurs champs et leur queryset filtré sous les préfixes `tasks_` / `milestones_` ; les choix de sources et `calendar_days` (7/14/21/30/60, défaut 14) restent dans la sidebar. Les deux renderers consomment le même payload `{window_start,today,window_end,earlier_overdue_count,events:[{id,source_type,source_label,date,title,project_name,project_href,secondary,href,state,tone,icon}]}`. La fenêtre commence à J-2 ; le compteur antérieur porte sur les échéances ouvertes en retard avant J-2, après visibilité et filtres propres à chaque provider. La grille ouvre le détail local d’un jour via le Popover existant, sans requête supplémentaire ni logique métier dans le renderer. Les renderers par défaut des sources individuelles restent `task-workload` et `deadline-list`.

Les clés source/widget doivent être uniques dans le plugin et face aux contributions déjà chargées ; les objets doivent être du bon type ; `compatible_renderers` ne peut être vide et `default_renderer` doit en faire partie. Toute contribution d’un plugin fautif est ignorée et journalisée. L’API vérifie existence, scope, multiplicité, taille, renderer compatible, et config : champs source/définition/renderer, types `string`, `boolean`, `integer`, `project`, `choice`, bornes, choix, champs inconnus et projet visible. Un renderer non core est admis par l’API seulement s’il correspond à `definition.renderer_key`, mais devra exister localement côté React. Les callbacks `available` qui échouent rendent la définition indisponible.

### Permissions, lifecycle et frontend bridge

Plugin actif → registre → `available_definitions` → `GET /api/v1/dashboards/catalog/` ou catalogue du Project → instance → appel batch des providers → [DashboardWidgetFrame](../../frontend/src/dashboard/DashboardWidgetFrame.tsx). Les types [DashboardCatalog, DashboardWidget](../../frontend/src/api/dashboards.ts) représentent les réponses. `DashboardWidgetEditor` fusionne les `config_fields` source/définition/renderer. L’API protège owner/contexte ; chaque provider doit encore utiliser les querysets visibles. Une définition disparue ou indisponible garde une instance montrable comme placeholder et supprimable ; une exception provider devient `error` avec `data=null`, sans casser tout le Dashboard.

Exemple minimal réel : `DataSource("core.note", "Note", "General", ("user",), ("empty",), provider, allow_multiple=True, default_renderer="empty", config_fields={"message": {"type": "string", "max_length": 500}})` ; le provider retourne `{ "message": config.get("message", "") }`. Les dataclasses et clés sont le contrat d’extension établi ; `dashboard_registry` et les détails de validation restent internes. Voir [tests ciblés](../../backend/dashboard/) et [exemple plugin](DASHBOARD_PLUGIN_EXAMPLE.md).

## Dashboard React renderers

### Purpose, location et registration

[renderers.ts](../../frontend/src/dashboard/renderers.ts) associe une clé backend à un composant React local. `DashboardRenderer = (props: {widget: DashboardWidget; size: DashboardSize; mode?: DashboardMode}) => ReactNode`. `RendererEntry = {component: DashboardRenderer; printComponent?: DashboardRenderer}`. `registerDashboardRenderer(key, renderer, printComponent?)` ajoute à la `Map` et jette une erreur sur clé dupliquée. `getDashboardRenderer(key, mode='view')` choisit `printComponent` pour `print` s’il existe, sinon le renderer normal. Les neuf renderers core sont enregistrés à l’import du module. `OverviewListRenderer` et `DeadlineListRenderer` lisent des payloads de présentation sans modèle métier ni calcul financier/temporel ; compact/standard/expanded ne changent que la densité. Tests : [dashboard frontend](../../frontend/src/dashboard/).

### Payload, validation, permissions, lifecycle et failure

Le composant reçoit `widget.data` via `DashboardWidget`, déjà choisi par l’API, ainsi que taille et mode ; il doit contrôler la forme du payload qu’il attend et ne pas créer un accès direct à des données hors scope. `DashboardWidgetFrame` gère titre, erreurs, indisponibilité, définition/renderer absent et contrôles selon le mode ; `DashboardWidgetEditor` consomme le catalogue de champs. Backend source → catalogue de clés → instance → données → résolution locale par clé → frame. Une clé backend sans composant local aboutit à l’état de renderer manquant. Exemple : une source plugin peut utiliser `compact-list` sans JavaScript plugin. Un renderer personnalisé nécessite un enregistrement **dans le bundle frontend local** ; le chargement dynamique de code frontend fourni par un plugin n’existe pas. L’API et `CORE_RENDERERS` ne deviennent pas automatiquement extensibles par cet enregistrement. Les signatures et clés sont des interfaces locales, la `Map` interne n’est pas publique.

## Print renderers

### Purpose, location et contract

Le registre [print/registry.ts](../../frontend/src/print/registry.ts) sépare la commande d’impression du rendu Calendar/Gantt/Organigramme/Dashboard. `PrintPage = {size: 'A4'|'A3'; orientation: 'portrait'|'landscape'}` ; `PrintRequest = {renderer: string; title: string; subtitle?: string; state: unknown; page?: PrintPage}` ; `PrintRendererProps<T=unknown> = {state: T; onReady: () => void}` ; `PrintRendererDefinition = {key: string; label: string; render: ComponentType<PrintRendererProps<never>>; defaultPage: PrintPage}`. La clé sélectionne le rendu ; le `state` est un snapshot local de la vue, dont le contrat précis appartient au renderer métier. Tests : [print.test.tsx](../../frontend/src/print/print.test.tsx) et [renderers.test.tsx](../../frontend/src/print/renderers.test.tsx).

### Registration, lifecycle, bridge, failure et stabilité

`registerBuiltinPrintRenderers()` enregistre une fois les quatre clés dans [renderers.ts](../../frontend/src/print/renderers.ts), à l’import de [PrintShell](../../frontend/src/print/PrintShell.tsx). `registerPrintRenderer(definition)` refuse les doublons ; `getPrintRenderer(key)` renvoie la définition ou `null`. `PrintButton` prépare la requête → `PrintProvider` garde la page montée et ouvre le shell → résolution du renderer → celui-ci appelle `onReady()` → le bouton imprime. Une clé inconnue affiche une alerte et désactive Imprimer ; la page demandée prime sur `defaultPage`, puis A4 paysage en fallback. Un renderer ajouté doit être importé et enregistré par le bundle frontend : **aucune API plugin Print ni chargement JS distant**. Exemple : `registerPrintRenderer({key:'calendar', label:'Calendar', render: CalendarPrintView, defaultPage:{size:'A4', orientation:'landscape'}})`. Le shell et la registry sont des points d’extension locaux ; les structures `state` de chaque renderer restent internes. L’impression reprend les données déjà chargées et ne doit pas élargir la visibilité.

## Global Search providers

### Purpose, location et discovery

Un provider représente un type de résultat, déclare ses champs, son queryset visible et sa destination React. Voir [contracts.py](../../backend/global_search/contracts.py), [registry.py](../../backend/global_search/registry.py), [engine.py](../../backend/global_search/engine.py), [autocomplete.py](../../backend/global_search/autocomplete.py), [providers.py](../../backend/global_search/providers.py), [business_providers.py](../../backend/global_search/business_providers.py), [organization_provider.py](../../backend/global_search/organization_provider.py), [SearchPluginMixin](../../backend/plugin/base/SearchPluginMixin.py), [tests](../../backend/global_search/). `SearchRegistry.register(provider)` ajoute les providers core à l’import (Employee, Project, Fund, Contract, Team, Organization) ; `active(user)` y ajoute `get_search_providers(user)` des plugins actifs. Collision, objet invalide ou erreur plugin : contribution du plugin entière ignorée et journalisée ; erreur de `available(user)` : provider masqué. `unregister(key)` ne concerne que les entrées core enregistrées en mémoire.

### Contract objects et callbacks

`SearchField` figé : `key: str`, `label: str`, `orm_paths: tuple[str,...]` obligatoires ; `type='text'`, `weight=50`. `as_schema` expose `contains` et `suggest_values`. `SearchProvider` est une classe à spécialiser : attributs `key=''`, `label=''`, `icon='Search'`, `fields=()`, `supports_generic_info=False`, `autocomplete=False`, `suggestable_fields=()`. Obligatoires en pratique : `visible_queryset(user) -> QuerySet` et `make_result(obj, *, score, match_reason) -> SearchResult`. `available(user)` vaut authentifié par défaut. `search_variants()` permet plusieurs sources ORM derrière une seule clé publique ; `prepare_candidates(candidates)` peut charger les relations. `field_query(field, term, lookup, user)` construit le filtre ORM ; `search_values(obj, field, user)` fournit des paires `(label, value)` pour rang/raison ; `generic_info_query/values`, `suggest_*` permettent GenericInfo et suggestions. Un override doit rester dans le queryset visible, avec requêtes bornées.

`SearchQuery` figé : `raw_text: str`, `free_text_terms: tuple[str,...]`, `provider_filter: str|None=None`, `field_filters: dict={}`, `ast: Any=None` ; `from_text` normalise les espaces. `SearchResult` figé : `provider_key`, `object_id`, `title`, `subtitle`, `url`, `score`, `icon`, `match_reason` et `metadata={}`. Les champs obligatoires sont des chaînes non vides sauf `subtitle` ; `score` est numérique positif ou nul ; `url` commence par `/app/`, sans `//`. `as_dict()` est le payload API. La destination doit pointer vers une fiche React visible, et la raison du match ne doit pas révéler une donnée cachée.

### Lifecycle, API, validation et failure

Providers actifs → schéma `/api/v1/search/schema/` → parser/AST de requête → conditions ORM sur `visible_queryset` → score exact > préfixe > contient et limite de candidats → `/api/v1/search/` → Topbar/page React via [client API](../../frontend/src/api/globalSearch.ts). `/api/v1/search/autocomplete/` utilise les mêmes providers/schémas, la position du curseur et les seuls objets visibles. Les champs GenericInfo sont traités par des callbacks spécifiques ; un provider sans `supports_generic_info` ne les promet pas. `SearchField.orm_paths` est une déclaration backend, non une permission. La syntaxe avancée n’accepte que les clés du schéma actif et rejette les expressions invalides en 400. L’interface suit `SearchResult.url` ; elle ne reconstruit pas une route selon le provider. Un provider manquant disparaît du schéma/onglets ; le plugin inactif n’est pas interrogé. Exemple existant : `OrganizationSearchProvider` regroupe deux sources, Institution et Fund_Institution, sous la clé `organization` tout en gardant deux résultats distincts et leurs routes propres. Les dataclasses/provider sont le contrat d’extension ; score, parser et fenêtre SQL sont des détails internes.

## Calendar events et filters plugins

### Purpose et location

Le noyau [common/calendar](../../backend/common/calendar/) normalise événements et filtres des domaines et plugins. [CalendarEventMixin](../../backend/plugin/base/CalendarEventMixin.py) les déclare ; [CalendarService](../../backend/common/calendar/service.py) les agrège ; [adaptateur React](../../frontend/src/calendar/fullCalendarAdapter.ts) traduit vers FullCalendar. Tests : [tests_calendar.py](../../backend/common/tests_calendar.py), [SharedCalendar.test.tsx](../../frontend/src/calendar/SharedCalendar.test.tsx), [fullCalendarAdapter.test.ts](../../frontend/src/calendar/fullCalendarAdapter.test.ts). La [façade legacy](../../backend/plugin/calendar_adapter.py) adapte les requêtes anciennes.

### Contract objects et callbacks

`CalendarType` accepte `main`, `team`, `employee`, `employee-gantt`, `project`, `project_all`, `employee_project` ; une valeur inconnue revient à `main`. `CalendarContext` figé : `calendar_type: CalendarType`, `user: Any` obligatoires ; `start/end: date|datetime|None`, `employee_id/project_id/team_id: int|None`, `filters: Mapping[str,Any]={}`. Le contexte représente une requête et son périmètre ; le plugin ne doit pas oublier l’utilisateur.

`LabsManagerCalendarEvent` figé : `id: str`, `title: str`, `start: date|datetime` obligatoires ; `end=None`, `source='core'`, `kind='event'`, `all_day=True`, `color=None`, `description=None`, `display='auto'`, `metadata={}`. `as_dict()` expose `id,title,start,end,source,kind,all_day,color,description,display,metadata` (dates ISO) ; `as_fullcalendar_dict()` sert le legacy avec `extendedProps`. Les clés métier dans `metadata`, notamment l’Employee/Leave, doivent être JSON-compatibles et respecter la visibilité. `LabsManagerCalendarFilterChoice(value: Any,label: str)` et `LabsManagerCalendarFilter(id,title,type,source,choices=(),default=None)` sont figés ; types bornés à `select`, `checkbox`, `radio`, `input-text`, `input-color`. `as_dict()` expose ces six champs, `choices` comme `{value,label}[]`.

`CalendarEventMixin` enregistre `calendarevent`. Ses classmethods : `get_calendar_events(context) -> list[LabsManagerCalendarEvent]` (défaut `[]`), `filter_calendar_queryset(queryset, context) -> queryset` (défaut inchangé), `get_calendar_filters(context) -> list[LabsManagerCalendarFilter]` (défaut dérivé de `FILTERS`). `FILTERS` associe une clé à `{title,type,choices?,default?}` ; `choices/default` peuvent référencer une classmethod sans argument ou acceptant `context`. Les filtres `select/checkbox/radio` nécessitent des choix ; les choix acceptent mapping ou paires ; l’ID normalisé est `source-slug(key)`. Les anciennes méthodes `get_filters(request,calendar_type,...)` et `build_filters()` sont des adaptations legacy, pas le nouveau contrat API.

### Registration, validation, permissions, lifecycle et bridge

`CalendarService.plugins()` sélectionne `registry.with_mixin('calendarevent', active=True)` ; la famille suit aussi `ENABLE_PLUGINS_CALENDAR`. Il applique chaque filtre de queryset puis agrège les événements core et plugin ; type de retour invalide ou exception est journalisé et isolé par plugin. Une définition de filtre invalide est sautée avec avertissement. Les APIs Calendar exposent `as_dict()` et les filtres normalisés ; `toFullCalendarEvent` conserve `description/source/kind/metadata` dans `extendedProps`, traduit `all_day`, `display` et les resources. Exemple réel : [FrenchHollidayPlugin](../../backend/plugin/samples/FrenchHollidayPlugin/FrenchHollidayPlugin.py) fournit des événements et filtres. L’activation du plugin ne donne aucun accès supplémentaire : les endpoints bornent l’Employee/Project et le plugin doit aussi respecter le contexte. Le service et les dataclasses sont le contrat partagé ; la forme spécifique de chaque `metadata` reste métier. Un plugin inactif ne fournit rien ; un événement illisible ne doit pas être masqué par un simple changement frontend.

## Import profiles

### Purpose, location et contract

L’allowlist [profiles.py](../../backend/import/profiles.py) expose les Resources héritées sans choix arbitraire de classe par le client. `ImportProfile` figé : `key: str`, `label: object`, `description: object`, `resource_class: type`, `permission: str` obligatoires ; `identity_columns: tuple[str,...]=()`, `join_identity=False`, `formats=('csv','tsv','xls','xlsx')`, `template_formats=('csv','xlsx')`, `preview_columns=()`. `allowed(user)` vérifie authentification et permission ; `metadata()` expose clé, libellés, formats et champs de preview ; `preview_fields(resource)` exige que les champs existent dans la Resource.

### Registration, callbacks, lifecycle et failure

`PROFILES` est un dictionnaire **statique**, actuellement `expense`, `employee`, `expense-timepoint` ; aucune contribution plugin. [api_v1.py](../../backend/import/api_v1.py) résout le profil à chaque étape et réutilise `django-import-export` : liste → template/upload → token signé → preview dry-run → commit. Permission `common.import` actuellement pour les trois profils ; elle reste configurable par profil. La Resource valide les données ; le profil choisit formats, identité et aperçu, pas les règles métier. Profil inconnu : 404 ; permission absente : 403 ; preview field invalide : `ImproperlyConfigured` ; format/token/fichier invalides : erreur API. Exemple d’ajout : déclarer une `ImportProfile('new-key', label, description, ResourceClass, 'app.permission', preview_columns=('field',))` dans `PROFILES`, avec tests d’import. API/React : [imports.ts](../../frontend/src/api/imports.ts), [tests API](../../backend/labsmanager/tests/test_api_v1_imports.py). Les clés de profil sont un contrat de client ; le stockage temporaire/token sont internes. Ne pas exposer de Resource non permissionnée par simple ajout de métadonnées.

## Mutable Settings Lists

### Purpose, location et contract

L’allowlist [mutable_lists_api_v1.py](../../backend/settings/mutable_lists_api_v1.py) permet au même éditeur React d’utiliser les ModelForms historiques sans branche métier côté client. `MutableList` figé : `group: str`, `model: type`, `form: type`, `columns: tuple[str,...]` obligatoires ; `ordering=('name',)`, `allow_delete=False`, `tree_column: str|None=None`. `GROUPS` fixe les groupes ; `MUTABLE_LISTS` fixe neuf listes. `allowed(user, action)` rend la lecture à l’utilisateur authentifié ; `add/change/delete` vérifient la permission modèle globale, et Delete exige aussi `allow_delete=True` (aucune liste actuelle).

### Registration, payload, validation, lifecycle et frontend

Ajout par déclaration statique dans `MUTABLE_LISTS` ; aucun plugin ni discovery. Le registre produit `GET /api/v1/settings/lists/` avec groupes/listes, champs `{key,label,type,required,readonly,choices,default}`, colonnes, `capabilities`; collection/détail renvoient les lignes `{id,values,capabilities,editable_fields,tree_level?}`. Types de champ : `relation`, `boolean`, `choice`, `color`, `text`. `tree_column` ajoute `renderers: {colonne:'tree'}` et `tree_level` ; seules Cost Type/Leave Type l’utilisent aujourd’hui. [client React](../../frontend/src/api/mutableLists.ts) rend selon ces métadonnées. Le ModelForm existant valide create/patch ; champs inconnus/désactivés sont rejetés ; `full_clean`, sauvegarde atomique et erreurs MPTT restent côté backend. Clé inconnue ou lecture interdite : 404 ; mutation interdite : 403 ; suppression protégée : erreur métier. Exemple : `MutableList('staff', Employee_Type, EmployeeTypeModelForm, ('name','shortname'))`. Les déclarations et payload sont le contrat actuel ; `row_data/save_form` sont internes. Tests : [test_api_v1_mutable_lists.py](../../backend/labsmanager/tests/test_api_v1_mutable_lists.py). Une entrée dans la liste ne doit jamais remplacer une vérification backend de permission.

## Data Consistency rules

### Purpose, location et registration

Le moteur [service.py](../../backend/data_consistency/service.py) détecte à la demande des incohérences sur des querysets visibles ; seules les exceptions humaines sont persistées. `RULES` est un tuple statique, indexé par `RULES_BY_KEY`, sans plugin ni fonction publique d’enregistrement. Neuf clés actuelles : `contract_employee_not_project_participant`, `contract_outside_project_dates`, `fund_outside_project_dates`, `contract_outside_employee_dates`, `milestone_outside_project_dates`, `task_outside_project_dates`, `contract_outside_fund_dates`, `expense_outside_fund_dates`, `project_without_leader`. Tests : [test_api_v1_data_consistency.py](../../backend/labsmanager/tests/test_api_v1_data_consistency.py).

### Contract objects, callbacks et issue payload

`ConsistencyRule` figé : `key: str`, `category: str`, `issues: object`, `serialize: object` obligatoires ; `object_type: str='contract'` parmi `contract/fund/milestone/expense/project`. Convention effective : `issues(user) -> QuerySet` **visible** et filtré aux anomalies ; `serialize(item) -> dict` contenant `rule_key`, `category`, `label`, `project_id` et l’ID propre à l’objet (`contract_id`, `fund_id`, `milestone_id`, `expense_id` ou `project_id`), avec noms/dates utiles. La couche générique s’appuie sur `IDENTITY_PATHS` et `OBJECT_ID_FIELDS` pour identifier l’occurrence ; une nouvelle famille d’objet nécessite d’étendre ces mappings et l’API, pas seulement d’ajouter un tuple. Exemple : `ConsistencyRule(PROJECT_LEADER_RULE_KEY, 'projects', projects_without_leader, project_without_leader_issue, 'project')`.

Les règles de dates partagent `outside_parent_dates` : une borne `null` est ouverte ; un parent borné ne contient pas un enfant ouvert du même côté. `date_fields` fournit `reason` (`starts_before_project`, `ends_after_project`, `both`), `parent_kind`, dates parent/enfant et, pour parent Project, `project_start_date/project_end_date`. Le libellé de reason est historique même lorsque le parent est Fund/Employee. La règle Participant ne vérifie que l’existence du couple Employee/Project, sans dates, et produit une issue par Contract.

### Exceptions, correction, permissions et lifecycle

Le modèle [DataConsistencyException](../../backend/data_consistency/models.py) conserve `rule_key`, IDs d’occurrence, `accepted_by`, `accepted_at`, `reason`, `closed_at`, `closed_reason`. Contraintes SQL : une seule exception ouverte par occurrence pour chaque famille d’objet. `active_issues` exclut via `Exists` les exceptions ouvertes ; `accepted_exceptions` ne retourne que celles dont l’issue est encore vraie et visible. `summary` compte côté SQL, par catégorie/règle. [signals.py](../../backend/data_consistency/signals.py) clôt les exceptions pertinentes lors des changements de relation/date et des résolutions ; ne pas dépendre du seul GET pour détecter un cycle résolution/réapparition. Les écritures bulk qui court-circuitent les signaux requièrent une vigilance propre à leur chemin d’écriture.

Les [API](../../backend/data_consistency/api_v1.py) : `GET /api/v1/data-consistency/summary/` avec `total`, `accepted_total`, `categories`, `rules`, `capabilities`; `GET /issues/?status=active|accepted&rule_key=...` paginé ; `POST .../accept/` revérifie l’issue/identité et renvoie 409 si obsolète ; `POST .../reopen/` clôt l’exception. Sans `rule_key`, la liste ne parcourt **que la première règle** ; le frontend doit demander chaque règle voulue. [permissions.py](../../backend/data_consistency/permissions.py) utilise `is_staff` ou les permissions `add/change_dataconsistencyexception` pour accept/reopen ; la lecture est authentifiée mais toujours bornée par les querysets visibles des règles. Les actions correctives React actuelles réutilisent les API métier Participant/Project/Fund/Employee et leurs capabilities ; elles ne font **pas** partie de `ConsistencyRule` ni d’un registre de callbacks correctifs backend. Issue active → correction métier ou acceptation distincte → refresh des issues/summary ; une acceptation n’effectue aucune correction. Une clé inconnue est rejetée, les doublons d’exception sont empêchés, une règle fautive n’est pas isolée automatiquement comme un plugin. Le tuple/serializer sont internes au dépôt ; les `rule_key` et champs API sont des identifiants persistants à préserver.

## Preference types

### Purpose, location et contrat

[preferences.py](../../backend/common/preferences.py) maintient `preference_types()` (cache d’un mapping statique) des types auxquels attacher favori/abonnement : `project`, `employee`, `team`, `institution`, `fund_institution`. `PreferenceType` figé : `model: type`, `group: str`, `react_path: str|None=None`. `group` classe la navigation ; `react_path` est un patron `/.../{id}` sous `/app` construit plus tard, ou `None` pour URL legacy. Ce n’est pas une API plugin ; les noms sont consommés dans les endpoints et le frontend. Tests : [tests preferences](../../backend/common/).

### Registration, lifecycle, permissions et failure

Pour ajouter un type, modifier la map, définir la visibilité dans `visible_objects`, la résolution d’URL legacy et la présentation attendue. `visible_objects` réutilise `get_instances_for_user('view')` pour Project/Employee, `visible_teams` pour Team et `common.display_infos` pour les organisations ; il recoupe le queryset d’entrée pour éviter son élargissement. `resolve_preference_object` refuse les objets invisibles (404). `type_for_content_type` traduit le ContentType ; un type inconnu lève `KeyError`. Favoris/abonnements sont stockés par GenericForeignKey, puis filtrés à la lecture ; les relations devenues invisibles restent en base sans être divulguées. [preferences_api_v1.py](../../backend/common/preferences_api_v1.py) expose GET/PUT du statut et listes de navigation ; [client React](../../frontend/src/api/preferences.ts) consomme ces noms/routes. Une nouvelle entrée ne donne aucun droit de voir l’objet. Mapping et fonctions de visibilité sont des contrats internes maintenus ensemble ; aucun enregistrement dynamique n’existe.

## Filtres déclaratifs de listes React

### Purpose, location et contrat

Les catalogues [config](../../frontend/src/config/) décrivent les filtres des pages Employee, Project, Contract, Team et outils financiers, consommés par [FilterBar](../../frontend/src/filters/FilterBar.tsx) et [FilterGallery](../../frontend/src/filters/FilterGallery.tsx). [types.ts](../../frontend/src/filters/types.ts) fixe `FilterOption={value:string,label:string}` ; `EntitySearchSource` a `search(query, signal) -> Promise<{options,hasMore}>` et `resolve(id,signal) -> Promise<FilterOption|null>` ; `ChoiceSource.loadAll(signal) -> Promise<FilterOption[]>`. `Base` donne `id,label,category` et `description/placeholder/defaultValue?`. `SupportedFilter` borne les contrôles actuellement rendables : `static-choice` avec `parameter/options`, `entity-search` avec `parameter/source/idFormat?`, `dynamic-choice` avec `parameter/source`, ou `text/date/number` avec `parameter`. Les définitions plus larges `FilterDefinition` incluent multi-valeur (`csv|repeat`) et plage (`lower/upper`) mais ne sont pas toutes branchées dans les catalogues vivants.

### Registration, validation, permissions, lifecycle et failure

Ce sont des fonctions/tableaux statiques importés par les pages, pas une registry à `register_` ni un mécanisme plugin. Définition → galerie/URL → sérialisation vers paramètres API → backend ; les sources asynchrones chargent des options et résolvent un identifiant pour l’affichage. Un `source` absent affiche l’état indisponible ; les tests de [FilterBar](../../frontend/src/filters/FilterBar.test.tsx) et d’[URL](../../frontend/src/filters/url.test.ts) couvrent le comportement. Exemple de déclaration : `{id:'active',label:'Active',category:'Status',type:'static-choice',parameter:'active',options:[{value:'true',label:'Active'}]}`. L’API backend doit prendre en charge le paramètre et appliquer visibilité/permissions ; un filtre React ne peut ni accorder un accès ni garantir à lui seul un scope. Ce catalogue est un contrat frontend interne, pas une interface d’extension plugin.

## Icônes GenericInfo et Organization

### Purpose, location et contrat

L’adaptateur [genericInfoIcons.ts](../../frontend/src/pages/genericInfoIcons.ts) associe un identifiant Lucide texte venant de la base à un composant déjà importé. Contrat : `icons: Record<string, LucideIcon>` privé ; `genericInfoIcon(name: string | null): LucideIcon` public pour les consommateurs. Le résultat est l’icône exacte si `name` est une clé propre de la map ; sinon `CircleQuestionMark`. [GenericInfoSection](../../frontend/src/pages/GenericInfoSection.tsx), [OrganizationDetailPage](../../frontend/src/pages/OrganizationDetailPage.tsx) et [HomePage](../../frontend/src/pages/HomePage.tsx) l’utilisent.

### Registration, lifecycle, validation et failure

Enregistrement uniquement par import et ajout explicite dans la map statique ; aucune découverte plugin, aucune API de registration runtime. La donnée backend fournit le nom de l’icône, jamais un composant React ni du HTML. Le fallback évite qu’une valeur historique/inconnue casse le rendu. Pour une nouvelle icône, importer le composant Lucide et ajouter sa clé, puis couvrir le mapping dans [genericInfoIcons.test.ts](../../frontend/src/pages/genericInfoIcons.test.ts). Ce mapping ne contrôle ni les permissions de lecture de l’information ni ses mutations. Il s’agit d’un adaptateur frontend interne, réutilisé par plusieurs métiers, et non d’un registre de plugins.

## État de la documentation et limites transversales

Les mécanismes Dashboard, Calendar, Print, Import et Mutable Lists figuraient déjà dans [ARCHITECTURE.md](ARCHITECTURE.md) et [REUSABLE.md](REUSABLE.md), mais leurs champs, collisions, payloads et états d’échec n’y étaient que partiellement décrits. Global Search était décrit par architecture/état ; Data Consistency, Preferences et filtres React demandaient une lecture du code pour établir le contrat exact. Les phrases historiques de [STATUS.md](STATUS.md) décrivent l’état **au moment de chaque lot** : par exemple le Dashboard n’est plus limité aux seuls contextes utilisateur et la Search ne se limite plus aux providers Employee/Project. Le code courant et ce document prévalent pour développer une extension. Aucun des registres frontend ici ne charge un bundle JavaScript fourni à l’exécution par un plugin ; les contributions backend ne peuvent rendre que les composants déjà présents dans le bundle React. Les registres statiques ne deviennent pas extensibles par plugin du seul fait qu’ils sont déclaratifs.
