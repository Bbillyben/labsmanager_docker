# Modèles Django des plugins externes

## Contrat `ModelMixin`

`ModelMixin` déclare une application Django **installée au démarrage**. Il ne crée ni modèle ni table et ne lance aucune migration. Le plugin héberge `apps.py`, `models.py` et ses migrations versionnées. `data/plugins/ModelExample/` est l'exemple complet fourni avec le dépôt ; ce répertoire n'entre pas dans l'image Docker (`Dockerfile` ne copie que `backend/`).

La classe du plugin hérite directement de `ModelMixin` et de `LabManagerPlugin`, et déclare des chaînes littérales `NAME`, `SLUG` et `DJANGO_APP`. Exemple : `DJANGO_APP = "plugins.ModelExample.apps.ModelExampleConfig"`. `plugins` est le nom du répertoire externe configuré, qui doit contenir `__init__.py`. L'`AppConfig` déclare `name = "plugins.ModelExample"` et un `label` unique tel que `model_example`. Conserver le nom du package, `AppConfig.name`, `AppConfig.label` et le slug après publication : les migrations, clés étrangères et références de modèles en dépendent. Les collisions entre apps et labels sont signalées au démarrage ; les collisions de slug impliquant un plugin avec modèles sont également refusées.

La découverte précoce lit seulement l'AST des fichiers Python des répertoires builtin, samples et externes configurés. Elle ajoute les `AppConfig` déclarés à `INSTALLED_APPS` avant `django.setup()`, sans importer le plugin ou ses modèles ni lire la base. Le registre habituel charge ensuite les plugins et vérifie la correspondance entre déclaration et application enregistrée. Il reste la référence pour les fonctions actives. La désactivation d'un plugin laisse son app et ses modèles installés tant que son code est présent. Ajouter ou retirer une app exige un redémarrage coordonné de tous les processus Django, y compris le worker ; recharger seulement le registre des plugins ne suffit pas.

## Installation et migrations

Copier le package et ses migrations dans le répertoire désigné par `LABSMANAGER_PLUGIN_DIR` ou `plugin_dir` (par défaut l'installation locale utilise `/home/labsmanager/data/plugins/`). Le répertoire doit être un package Python et le chemin doit être stable. Installer d'abord toute dépendance Python nécessaire aux imports de `apps.py` et `models.py` avec le gestionnaire existant, puis redémarrer les processus. Les dépendances ne sont jamais installées pendant la lecture des settings. Pour `ModelExample`, aucune dépendance supplémentaire n'est nécessaire.

Le développeur crée une nouvelle migration avec `python manage.py makemigrations model_example`, la conserve dans le package, puis distribue le package mis à jour. L'administrateur vérifie et applique avec `python manage.py showmigrations model_example`, `python manage.py migrate --plan`, puis `python manage.py migrate model_example --noinput`. Ces commandes détectent l'app externe avant l'initialisation du registre Django ; la base réelle n'est modifiée que par `migrate`. Le contrôle `migrate --check` de `init.sh` reste en place et refuse un démarrage normal si une migration manque.

Pour tester `ModelExample` en bare metal depuis le dépôt, définir `LABSMANAGER_PLUGINS_ENABLED=true` et `LABSMANAGER_PLUGIN_DIR=<racine du dépôt>/data/plugins` pour les commandes `backend/manage.py check`, `showmigrations model_example`, `migrate model_example` et `shell`. Dans le shell : `from django.apps import apps; Record = apps.get_model("model_example", "ExampleRecord")`. Les tests automatisés ciblés utilisent une base Django isolée : `python backend/manage.py test plugin.test_model_mixin --noinput` avec les mêmes variables d'environnement.

## Déploiement Docker avec volume persistant

1. Copier `data/plugins/ModelExample/` sur l'hôte dans `<LAB_EXT_VOLUME>/plugins/ModelExample/`. Le package parent `<LAB_EXT_VOLUME>/plugins/` doit contenir `__init__.py`. La configuration `LABSMANAGER_PLUGIN_DIR` de l'image doit pointer vers `/home/labsmanager/data/plugins` ; `LABSMANAGER_PLUGINS_ENABLED` doit être actif. Le code et les données PostgreSQL résident sur le volume persistant, hors de l'image.
2. Vérifier que les dépendances du plugin sont présentes dans l'environnement Python de l'image ou dans la release gérée partagée. Une nouvelle release exige un nouveau démarrage des processus Django.
3. Démarrer PostgreSQL seul si nécessaire : `docker compose up -d lab-db`. Avec la même image, le même fichier `.env`, les mêmes volumes et le même réseau que le serveur, exécuter un conteneur ponctuel qui contourne uniquement l'entrypoint de démarrage : `docker compose run --rm --no-deps --entrypoint python3 lab-server /home/labsmanager/labsmanager/manage.py showmigrations model_example`, puis la même commande avec `migrate model_example --noinput`. Cette méthode fonctionne même si `lab-server` ne démarre pas à cause de `migrate --check` ; elle n'utilise pas `docker compose exec`.
4. Démarrer ou recréer `lab-server` et `lab-worker` avec la même image (`docker compose up -d --no-build`). Les deux chargent l'app depuis le volume. Une mise à jour de l'image conserve le plugin et sa table tant que le volume et la base PostgreSQL sont conservés. Ne pas supprimer les volumes.

Supprimer physiquement le code du plugin ne supprime jamais ses tables ni ses données. Django ne peut plus importer ses modèles et certaines migrations ou références d'autres apps peuvent alors empêcher le démarrage ou de futures migrations ; analyser ces dépendances et conserver une sauvegarde avant tout retrait. Aucune migration inverse n'est exécutée automatiquement.
